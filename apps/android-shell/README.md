# @mykhaya/android-shell

Capacitor native Android shell for MyKhaya. This package does **not** contain
a second copy of the MyKhaya frontend — it configures a native Android
WebView that loads the real, deployed `apps/web` origin ("live frontend"
model), the same architecture already used by
[`apps/ios-shell`](../ios-shell/README.md). See
[ADR 0014](../../docs/architecture/adr/0014-capacitor-android-shell.md) for
the full architecture decision, and
[ADR 0012](../../docs/architecture/adr/0012-capacitor-ios-shell.md) (the
equivalent iOS decision) and
[ADR 0011](../../docs/architecture/adr/0011-single-pwa-retire-mobile-app.md)
for why this is a thin shell and not a second frontend implementation.

**Phase 1 only.** This package currently establishes the shell and a
development build. It intentionally does **not** yet implement push
notifications (FCM), notification channels/permissions, biometric unlock,
Android App Links, Play Billing, or widgets — see "What's intentionally not
implemented yet" below.

## What lives here vs. what doesn't

- **Here:** `capacitor.config.ts` (which live frontend origin to load, and
  the explicit `allowNavigation` allow-list), a minimal `www/index.html`
  fallback page, and the native `android/` Gradle project (**committed to
  git**, mirroring `apps/ios-shell/ios/` — see below).
- **Not here:** any MyKhaya UI. Ordinary web/PWA feature work happens in
  `apps/web` exactly as before and reaches this shell automatically on next
  app launch, with no new Play Store release, because the shell always
  loads the live origin.

## The native `android/` project is committed — this is not a build artifact

Mirroring `apps/ios-shell/ios/`'s own rationale, **this repository commits
`apps/android-shell/android/`** so a fresh clone gets a complete, working
Gradle project rather than requiring `cap add android` to be re-run (which
would only be a recovery step, not routine setup). Build outputs
(`build/`, `.gradle/`), machine-specific config (`local.properties`), and
Capacitor's own regenerated copies (`app/src/main/assets/public/`,
`app/src/main/assets/capacitor.config.json`, `capacitor.plugins.json`,
`app/src/main/res/xml/config.xml`) are gitignored (`android/.gitignore`,
generated by Capacitor's own template) — only the project structure,
source, and configuration needed to reconstruct a working build are
tracked.

## Windows-friendly commands

All of these run on Windows (or Linux/macOS) with no Android Studio
required, mirroring `apps/ios-shell`'s "plain TypeScript is Windows-first"
approach:

```sh
pnpm install                                       # from the repo root
pnpm --filter @mykhaya/android-shell typecheck     # tsc --noEmit
pnpm --filter @mykhaya/android-shell test          # vitest — config.ts's logic
```

Editing `capacitor.config.ts` or `src/config.ts` (which live frontend origin
a build points at, the `allowNavigation` list, the app identifier) is plain
TypeScript — fully editable and testable from Windows.

```sh
npx cap sync android    # copies capacitor.config.ts + www/ into android/ after any change to either
```

`cap sync android`'s file-copy/config-generation step itself needs no Java —
verified in this environment (no JDK installed) — but it does not compile
or run anything; see "Building and running" below for what actually needs
the Android SDK/a JDK.

## Building and running (needs Android Studio / Android SDK + a JDK)

```sh
npx cap open android    # opens Android Studio
cd android && ./gradlew assembleDebug   # builds a debug APK from the command line
```

`cap sync android` needs re-running only when `capacitor.config.ts`, `www/`,
or a native plugin dependency changes — never for an ordinary `apps/web` UI
change, which the live shell picks up on its own.

**This environment does not have a JDK/Android SDK installed**, so the
Gradle build itself has not been executed here — only statically verified
(project structure, Gradle file references, and the generated
`capacitor.config.json` were inspected and are structurally correct). Real
runtime/device verification is still required before this ships — see the
Phase 1 completion report for exactly what was and wasn't verified.

## Environment selection

`MYKHAYA_ANDROID_ENV` (`development` | `production`, default `development`)
selects which live frontend origin a build points at — see `src/config.ts`.
Production builds must set `MYKHAYA_ANDROID_ENV=production` explicitly. The
native API uses the same frontend origin's `/api/v1` route in both
environments. There is no separate `.env` file for this package; it is a
single named variable, the same `MYKHAYA_`-prefixed convention used
throughout the backend and by `apps/ios-shell`'s `MYKHAYA_IOS_ENV`.

```sh
MYKHAYA_ANDROID_ENV=production npx cap sync android
```

## Application identity

`app.mykhaya.mobile` — reused from the retired `apps/mobile` Expo app's own
`android.package` configuration (its final `app.config.ts`, before ADR 0011
retired it, set `android: { package: "app.mykhaya.mobile" }` — the exact
same identifier already reused for iOS's `appId` in ADR 0012). Using the
same identifier on both platforms was an explicit historical precedent, not
a new naming decision. **Not yet registered with a real Google Play Console
account** — needs Anthony's explicit confirmation before that happens, the
same posture ADR 0012 already established for the iOS bundle ID.

## Security configuration

- `server.cleartext: false` — HTTPS only, both environments.
- `server.allowNavigation` — a short, explicit, non-wildcard host list (just
  the live frontend's own hostname), mirroring `apps/ios-shell`'s policy
  exactly. Never grown to include a third-party domain "to fix" a broken
  navigation — a regression test (`src/config.test.ts`) asserts this.
- `AndroidManifest.xml`: `android:usesCleartextTraffic="false"` (explicit,
  defense-in-depth alongside Capacitor's own bridge-level cleartext check),
  `android:allowBackup="false"` (no app data included in Android Auto
  Backup — the Android analogue of the iOS Keychain session store's
  `whenUnlockedThisDeviceOnly`/never-iCloud-synced posture; there is no
  legitimate reason yet for this shell's data to be backed up), and only the
  `INTERNET` permission — no camera, notifications, contacts, location, or
  storage permissions, since none of those capabilities exist in this shell
  yet.

## What's intentionally not implemented yet

Deferred to later Android phases (see the audit/phased plan referenced in
ADR 0014) — present in the shared web app already but inert or unreachable
on this platform until each phase lands:

- **Push notifications (FCM)** — no Firebase dependency, no
  `google-services.json` (never commit one — see `android/.gitignore`), no
  notification channels/permissions. `apps/web/components/native-push.ts`'s
  native push functions remain gated to iOS only.
- **Biometric unlock** — no `BiometricPrompt` configuration.
- **Android App Links** — no `assetlinks.json`, no manifest intent-filter
  for `https://` MyKhaya links; tapping one currently opens the browser, not
  the app (the same gap iOS has today, per ADR 0012).
- **Google Play Billing** — no purchase flow; `SubscriptionProvider.google`
  is a reserved-but-unimplemented enum value in the backend.
- **Widgets** — no Android App Widgets / Glance equivalent of the iOS
  WidgetKit widgets.
- **Native diagnostics enhancements** — the About page's "Push provider"
  and native-app-label strings are still iOS-flavoured; harmless (they
  simply won't reflect Android accurately yet), not fixed in this phase.

None of the above blocks the shell from loading and displaying the shared
MyKhaya UI — see the Phase 1 completion report for the current known-open
questions around Android WebView compatibility (safe-area CSS behaviour,
back-button handling) that still need real-device verification.
