## Authority and source documents

This standard governs work on the native iOS app (`apps/ios-shell`) and on
`apps/web` changes that can affect it. It supplements, and does not replace:

- `AGENTS.md`, [Engineering Standards](engineering-standards.md),
  [Mobile Standards](mobile-standards.md),
  [UI Platform Standards](ui-platform-standards.md),
  [Definition of Done](definition-of-done.md),
  [Git Branching Strategy](git-branching-strategy.md) and
  [Versioning and Releases](versioning-and-releases.md);
- [iOS DEV and PROD apps](../mobile/ios-environments.md): the **authoritative**
  DEV/PROD identity matrix. This standard deliberately does not copy it;
- [iOS Home Screen Widgets](../mobile/ios-widgets.md) and the
  [iOS Shell Mac/Xcode Checklist](../mobile/ios-shell-mac-checklist.md);
- ADRs [0010](../architecture/adr/0010-mobile-bearer-session-tokens.md) (bearer
  sessions), [0012](../architecture/adr/0012-capacitor-ios-shell.md) (Capacitor
  shell) and [0013](../architecture/adr/0013-hybrid-web-and-native-presentation.md)
  (hybrid presentation).

Inspect current code before relying on phased implementation notes in older
documents. Where a document and the implementation disagree, stop, flag the
difference and update both once the intended behaviour is decided
([Engineering Standards, Authority](engineering-standards.md#authority)).

## 1. Architecture rules

- MyKhaya has **one** primary frontend, `apps/web`. The iOS app
  (`apps/ios-shell`) is a Capacitor WKWebView wrapper and native capability
  boundary, not an independent SwiftUI feature implementation.
- The installed app loads the **live HTTPS frontend**. Ordinary `apps/web`
  changes reach it on next launch once that frontend is deployed; they need no
  new IPA. Native Swift, plugin, entitlement, widget, Info.plist, signing and
  version changes need an Xcode build and normally App Store distribution.
- `MainViewController.instanceDescriptor()` takes the live host from the build
  configuration (Info.plist `MyKhayaServerHost`), sets it as the server URL and
  makes it the **only** allowed navigation host. If the build configuration has
  no valid environment it calls `fatalError` rather than guess. Do not weaken
  this to a fallback.
- `capacitor.config.json` is generated by `cap sync`, is git-ignored and is
  **not** what the installed app loads. Never infer DEV/PROD identity from it.
  `capacitor.config.ts` (`MYKHAYA_IOS_ENV`, default `development`) only feeds
  Capacitor CLI fields (`appId`/`appName` for `cap add`, the scheme `cap run`
  builds).
- `ios.contentInset` is `"never"`: all safe-area handling belongs to
  `apps/web` CSS (`env(safe-area-inset-*)`, `viewport-fit=cover`). Do not switch
  it back to `"automatic"`; that stops `env(safe-area-inset-*)` resolving in
  WKWebView.
- **Native cold-start bootstrap.** `MainViewController.capacitorDidLoad()`
  injects a document-start script that replaces a plain restored `/login` with
  `/` on a cold native document, so iOS restoring a stale public URL cannot
  bypass the server-selected acquisition gate. Widget deep links set the
  `mykhaya.native.deep-link-start` session marker first and are exempt. Keep
  `src/native-startup-bootstrap.test.ts` passing when touching either side.
- The storyboard owns the window and bridge view controller
  (`ensure-storyboard-scene-delegate.sh`, `src/scene-delegate-bootstrap.test.ts`).
  Do not add programmatic window/bridge setup to `SceneDelegate`.
- Keep authentication, permissions, entitlements, Home isolation, domain logic
  and API contracts shared and server-enforced. Hiding UI is not authorisation.
- Use the canonical `isNativeShell()` and `nativePlatform()` from
  `apps/web/components/native-runtime.ts`. No scattered Capacitor checks, no
  user-agent device detection.
- Browser cookie authentication and native Keychain bearer sessions stay
  separate (ADR 0010). Never write bearer or device tokens to web storage or logs.

## 2. Native source ownership

| What | Canonical source (edit here) | Installed into | By |
|---|---|---|---|
| App-target Swift (`MainViewController`, `WidgetBridgePlugin`, `SystemSettingsPlugin`, `NativePushEnvironmentPlugin`) | `apps/ios-shell/native/plugin/` | `ios/App/App/` (tracked copies) | `scripts/install-widget-sources.sh` |
| Widget extension sources, Info.plist, entitlements | `apps/ios-shell/native/widgets/` | `apps/ios-shell/MyKhayaWidgets/` (git-ignored) | `scripts/install-widget-sources.sh` (rsync `--delete`) |
| Shared widget logic and its tests | `apps/ios-shell/native/WidgetCore/` (local Swift package) | linked into both targets | `scripts/link-widget-core-package.rb` |
| Environment identity, version, build, signing team | `ios/App/Config/Environment-{Dev,Prod}.xcconfig` | both targets via the four build configurations | Xcode |

- Always change the canonical file and re-run the installer, then commit the
  canonical file **and** the regenerated tracked copy together.
  `src/native-source-copies.test.ts` fails if a tracked copy differs from its
  `native/plugin` source, or if the installer does not copy a `native/plugin`
  file. The untracked widget copy (`MyKhayaWidgets/`) can only be checked on
  the Mac (`diff -r native/widgets MyKhayaWidgets`).
- Repo-local plugins are not auto-discovered: each is registered in
  `MainViewController.capacitorDidLoad()`. A new repo-local plugin needs the same.
- npm Capacitor plugin versions in `apps/ios-shell/package.json` must match
  `apps/web` exactly (`src/plugin-ownership.test.ts`).
- The Xcode project is committed. `npx cap add ios` is recovery-only. Change
  targets and phases through the existing Ruby/xcodeproj scripts, not by
  regenerating the project.

## 3. DEV and PROD isolation

The identity matrix (names, bundle IDs, widget IDs, App Groups, URL schemes,
hosts, schemes, configurations, APNs environment, team) is in
[iOS DEV and PROD apps](../mobile/ios-environments.md) and the two
`Environment-*.xcconfig` files. Do not restate it elsewhere. Rules:

- Every environment value is set once, in `Environment-Dev.xcconfig` or
  `Environment-Prod.xcconfig`. Targets, entitlements and Info.plists refer to
  `$(MYKHAYA_*)` settings, never literals. Shared native code reads the
  environment from Info.plist (`MyKhayaEnvironment` and related keys) and must not
  hardcode either environment.
- Do not set bundle IDs, signing, Version or Build in Xcode's General or
  Signing & Capabilities panes. They write target-level overrides, which the
  **Validate MyKhaya environment** build phase and the tests reject.
- APNs environment comes from the build configuration
  (`MYKHAYA_APNS_BUILD_ENVIRONMENT`): `development` for `Debug-*`, `production`
  for `Release-*`. That covers TestFlight and App Store builds of **both** apps.
- **Versioning:** each environment has its own `MARKETING_VERSION` and
  `CURRENT_PROJECT_VERSION`. Builds count from 1 within each version, DEV may
  lead PROD but never trail it, and the widget always carries its app's
  version and build ([Versioning and Releases](versioning-and-releases.md#ios-app-version-and-build-numbers)).
  This replaced the earlier global build counter (last used: `0.1.33 (112)`) on
  27 October 2026 (`c5c2190`).
- Both apps must coexist on one device with separate Keychain items, App
  Group data, push registrations and URL schemes. A widget link carrying the
  other environment's scheme is ignored by `WidgetBridgePlugin`.
- **Backend APNs topic.** The API sends with `apns-topic` =
  `MYKHAYA_APNS_BUNDLE_ID`, and each backend serves one app. The DEV backend
  needs `app.mykhaya.mobile` and the PROD backend `app.mykhaya.mobile.prod`. A
  topic mismatch is rejected by APNs, and the worker then **disables** the
  device registration. See [§9](#9-known-open-issues).

Checks: `pnpm --filter @mykhaya/ios-shell test` (any OS),
`sh scripts/validate-ios-environments.sh` from `apps/ios-shell` (Mac,
expanded build settings and schemes), and `swift test` in
`native/WidgetCore` when widget or environment code changes.

## 4. Protected standard iPhone and iPhone Duo layouts

### Native layout states

`AppShell` sets these classes on `.app-shell`, only inside the native shell,
from media queries in `apps/web/components/native-layout.ts` plus a measured
right safe-area inset:

| Class | Condition |
|---|---|
| `native-wide-viewport` | width ≥ 760pt (`NATIVE_WIDE_QUERY`) |
| `native-compact-rail` | not wide, and 450–759pt wide and 450–800pt tall (`NATIVE_COMPACT_RAIL_QUERY`) |
| `native-right-column` | compact rail, or wide and height ≥ 521pt (`NATIVE_RIGHT_COLUMN_QUERY`) |
| `native-status-column` | right column **and** a non-zero right safe-area inset |

Which devices get which state:

| Presentation | Classes |
|---|---|
| Standard iPhone portrait | none: the protected compact baseline |
| Standard iPhone landscape, under 760pt wide | none |
| Standard iPhone landscape, 760pt or wider (larger models) | `native-wide-viewport` only, with the short-screen rules |
| iPhone Duo outer (closed) screen | `native-compact-rail native-right-column native-status-column` |
| iPhone Duo inner (unfolded) screen | `native-wide-viewport native-right-column native-status-column` |
| iPad full screen | `native-wide-viewport native-right-column` |
| iPad Stage Manager or split window, 450–759 × 450–800pt | `native-compact-rail native-right-column` (no status column) |

### Rules

- **Never modify standard iPhone portrait or landscape by accident while
  changing Duo or iPad layouts.** Because larger iPhones in landscape match
  `native-wide-viewport`, a rule meant only for the Duo or iPad must be scoped
  with `native-right-column` or `native-status-column`, not
  `native-wide-viewport` alone. Never identify hardware by user agent.
- Duo outer and inner screens are two presentations of the same frontend.
  Scope styles to the classes above. Protect the standard iPhone bottom
  navigation, sheets, FABs and header.
- The app shell owns the shared notifications/profile pill. Do not duplicate or
  reposition it per page. Current behaviour (`3118574`): on both Duo screens
  the pill sits in the shell's header bar on every route. Test the notification
  tray, profile sheet, unread badge, keyboard focus and overlay stacking on each
  affected presentation. The header is its own stacking context and is raised
  above the fixed rail in rail layouts so sheets it hosts cover the rail
  (`2652a84`).
- Keep one coherent right-hand column for the navigation rail, Calendar tools
  and floating Add buttons, on a consistent centreline, with 44×44 targets, and
  **never covering page content**. Re-measure the dock if entitlements change
  its destinations. No scattered fixed offsets.
- The right safe-area inset is not the drawn status indicator. Physical Duo
  measurements (`4ca114f`): the status column needs about 165pt of top
  clearance folded and about 106pt unfolded, with a right inset of about 93pt
  on the outer screen. Re-measure on hardware after any iOS update rather than
  centring on the inset.
- Calendar month view and the selected-day pane share selection and filter
  state. Preserve recurrence, all-day and multi-day events, colour labels,
  visibility, create/edit permissions and overflow ("+N more") access. Limit
  density without dropping data.
- Avoid portrait-style oversized headers in wide mode, horizontal overflow,
  overlapping fixed elements, short-window collisions and unreachable floating
  controls. Include iPad and Stage Manager cases.
- Whether a header or pill is sticky or scrolls is a UX decision that needs
  route-wide validation, not a CSS-only assumption. The Duo pill changed three
  times between 23 and 25 October 2026 (`2652a84`, `f2eec12`, `3118574`). Agree
  the behaviour against mockups before changing it again.
- Encode each layout decision in the CSS contract tests
  (`apps/web/styles-native-wide-*.test.ts`, `components/app-shell.test.tsx`),
  including a case proving standard iPhone and iPad are unaffected. These tests
  are regression guards, not device sign-off.

## 5. Native security and integration

**Sessions and Keychain** (`components/keychain-native-session-store.ts`)

- The session token and the TrustedDevice renewal token are stored as separate
  Keychain items, each with `KeychainAccess.whenUnlockedThisDeviceOnly` and
  `sync: false` passed on every call. Never use an unencrypted or JS-side
  fallback.
- A Keychain read failure is not "signed out". The credential is preserved and
  AuthProvider shows offline/retry. Do not convert errors into logout.
- 401 handling is compare-and-clear (ADR 0010): only clear the stored token if
  it is the one that failed.

**Biometrics** (`native-biometric*.ts`, `native-app-lock.ts`)

- On a cold launch with biometrics enabled, the challenge completes before the
  bearer session is read. Cancellation or failure keeps the Keychain session
  but never unlocks the app; it offers retry or password.
- Resume re-locks after `BIOMETRIC_LOCK_TIMEOUT_MS` (5 minutes) in the
  background. A short task switch does not prompt, and the first
  `appStateChange` at startup is not treated as a resume. Keep these in the one
  exported constant and decision function.
- Known limitation: the session item is not bound to `biometryCurrentSet`
  (the plugin exposes no `SecAccessControl`). Closing this needs a small native
  Keychain bridge (ADR 0012).
- Browser/PWA passkeys and native Quick Sign-In are separate code paths. Do not
  merge them.

**Push** (`components/native-push*.ts`, `NativePushEnvironmentPlugin.swift`,
`apps/api/mykhaya/notifications/push.py`)

- Native push uses APNs via `@capacitor/push-notifications`, never the
  service-worker/VAPID path, which is skipped in the shell.
- The web layer gets the APNs environment from `NativePushEnvironmentPlugin`,
  which reads the signed build's `MyKhayaAPNsEnvironment`. Never infer it from
  the API host. The backend stores it per registration and selects the sandbox
  or production endpoint per device.
- APNs credentials are backend-only secrets. Never log device tokens, `.p8`
  keys, session tokens, raw APNs errors or personal payloads (`AppDelegate`
  logs presence and category only).
- Notification-tap paths go through `safeNativePushPath()`.

**Widgets** ([iOS Home Screen Widgets](../mobile/ios-widgets.md))

- Widget data is a versioned, display-only snapshot written to the matching
  environment's App Group. It never contains tokens, cookies or PINs. Bump the
  schema version on both sides for breaking changes. The extension treats an
  unknown version as "no data".
- Logout replaces the snapshot with a signed-out placeholder and reloads
  every widget timeline. App and widget versions and builds always match.
- Lock Screen redaction (`.privacySensitive()`) is not implemented yet.

**Navigation and external links**

- External links use `openExternalUrl()` (`@capacitor/browser`, in-app
  Safari view), never a top-level navigation of the authenticated WebView.
- Do not add third-party hosts, and never wildcards, to the allowed navigation
  hosts to work around a flow. Stripe billing still uses top-level navigation
  and is an open decision ([§9](#9-known-open-issues)).
- Preserve server authorisation, feature flags, child restrictions and
  platform-administration isolation. An iOS redesign is not grounds for
  changing API permissions.
- Keep `PrivacyInfo.xcprivacy` and the Info.plist usage descriptions accurate
  when adding a capability or API that needs a reason code.

## 6. Physical validation and acceptance

Browser harnesses, Playwright screenshots and CSS contract tests are useful but
are **not physical iOS sign-off**. During the Duo work, selectors that passed in
Chromium did not apply to the real outer screen. For iOS-visible changes,
record:

1. The Git source SHA **and** the deployed live frontend SHA. A push is not a
   deployment.
2. Xcode scheme, build configuration and bundle ID, when a native build is
   involved.
3. Device, iOS version, outer or inner screen, rotation, CSS viewport in points,
   measured safe-area insets, and which native layout classes were active.
4. Physical screenshots of affected routes, compared with the approved mockups.
5. Scroll, overlay, toolbar, FAB and rail collisions, and whether the
   notification tray and profile sheet work.
6. Regression evidence on a **standard iPhone in portrait and landscape**
   (including a 760pt+ landscape model), plus iPad and Stage Manager or
   short-height cases where relevant.
7. Real Dynamic Type or web text-scaling behaviour, kept distinct from
   simulated browser zoom.

UI acceptance also requires 44×44 CSS px touch targets, keyboard and focus
navigation, no obscured content and an accessibility review. Do not claim iOS
validation when only Windows or Chromium tests ran. Keep private family and
child data out of screenshots shared in issues or PRs.

The `quality` workflow's `ios-shell` job runs `pnpm --filter @mykhaya/ios-shell
typecheck` and `test` on every push and PR to `dev` and `main`. It needs no Mac.
Xcode builds, `validate-ios-environments.sh` (with real `xcodebuild` output) and
`swift test` still run only on the Mac.

## 7. Mac and Xcode workflow

1. `git fetch origin`. Inspect the branch, `git status --short
   --untracked-files=all`, unpushed commits and ignored native files. Do not
   overwrite or discard Mac changes.
2. Work on `dev`. Promotion to `main`, release tags and PROD deployment require
   the owner's approval ([Git Branching Strategy](git-branching-strategy.md)).
3. Use `apps/ios-shell/scripts/mac-bootstrap.sh` (or
   `install-widget-sources.sh` on an already set-up checkout). The bootstrap
   refuses a dirty working tree, never switches branches for you, and
   requires an explicit `MYKHAYA_IOS_REF` (branch or full 40-character SHA)
   for a production run. It prints tool versions for the handoff.
4. Validate with `pnpm --filter @mykhaya/ios-shell test`,
   `sh scripts/validate-ios-environments.sh` from `apps/ios-shell`, and
   `swift test` in `native/WidgetCore` where changed.
5. Open `ios/App/App.xcodeproj`. Select `MyKhaya-Dev` (runs `Debug-Dev`) or
   `MyKhaya-Prod` (runs `Debug-Prod`). `MyKhayaWidgets-*` schemes build the
   widget alone and are not the app.
6. Build and test the actual DEV app on supported devices. Report the exact
   build result, Xcode version, device screenshots and limitations.
7. Commit native changes through `scripts/mac-commit.sh` (or an equivalent
   review). Never commit certificates, private keys, provisioning profiles,
   generated credentials, archives, `xcuserdata` or DerivedData. Check staged,
   unstaged, untracked **and ignored** paths for important native source
   before handoff. The generated `MyKhayaWidgets/` copy is meant to stay
   ignored.

From `apps/ios-shell`:

```sh
pnpm --filter @mykhaya/ios-shell test
sh scripts/validate-ios-environments.sh
xcodebuild -project ios/App/App.xcodeproj -scheme MyKhaya-Dev  -configuration Debug-Dev  -sdk iphonesimulator build
xcodebuild -project ios/App/App.xcodeproj -scheme MyKhaya-Prod -configuration Debug-Prod -sdk iphonesimulator build
```

A simulator build is not evidence that signing, native runtime appearance,
physical-device push or App Store submission works.

## 8. DEV-to-PROD and App Store submission

1. Confirm all approved Mac and Windows changes are committed and pushed to
   `origin/dev`. Review the latest PR, CI, divergence and requested changes
   before the owner merges to `main`.
2. Check the **deployed** DEV frontend commit separately from Git. Test DEV on
   physical devices first.
3. On the Mac, check out the approved `main`. Check App Store Connect's latest
   version and build for the PROD app, then set `MARKETING_VERSION` and
   `CURRENT_PROJECT_VERSION` in `Environment-Prod.xcconfig` only (PROD never
   ahead of DEV).
4. Select `MyKhaya-Prod` and archive (`Release-Prod`). Inspect the app and
   widget bundle IDs, entitlements (`aps-environment` = `production`), origin,
   App Groups, signing, privacy manifest and widget payload.
5. Upload to the **existing PROD App Store Connect app**. Uploading is not
   TestFlight approval, App Review submission or publication. Each needs
   separate approval.
6. On TestFlight, validate on physical devices: production APNs **delivered
   through the PROD backend** (topic `app.mykhaya.mobile.prod`), persistent
   Keychain, biometric launch, widgets, deep links, support/privacy details,
   reviewer access or demo fixture, and store metadata.
7. Because the shell loads a **live frontend**, an archive does not publish new
   UI on `mykhaya.app`. Check the PROD web deployment and its SHA separately, and
   coordinate any backend dependencies and rollback.

## 9. Known open issues

Verified from repository contents on 28 October 2026. Re-check before acting.

- **PROD APNs topic.** `.env.production.example` and the ios-shell README now
  give `app.mykhaya.mobile.prod`, and the production deploy validator
  (`validate_backend_config.py`) rejects any other topic when APNs delivery is
  on. The `compose.yml` worker fallback and the `apns_bundle_id` code default
  are still the DEV bundle, so production must set the value explicitly.
  Whether the live PROD server sets it correctly is unverified.
- **Stripe billing in the shell.** `settings/billing` still navigates the
  WebView to Stripe with `window.location.href`, which the single-host
  allow-list blocks (ADR 0012's open decision).
- **Biometric binding.** Keychain items are not bound to the enrolled biometry
  set ([§5](#5-native-security-and-integration)).
- **Widget Lock Screen redaction** is not implemented.
- **Product-quality follow-ups to reproduce, not yet confirmed defects:**
  standard iPhone landscape FAB overlap reported during the Duo work, rail/FAB
  collisions in very short windows, real Dynamic Type behaviour, notification
  and profile overlay clearance across the shell, and cross-route native tests.

## 10. What this standard has and has not verified

Verified against the repository: the two-app xcconfig matrix, the four build
configurations and their base xcconfigs, the four shared schemes and their
Run/Archive configurations, entitlements and Info.plist variable wiring, the
build-phase and test validators (91 ios-shell tests passing), native plugin
sources, Keychain, biometric, push and widget code paths, and the native
layout-state logic.

Not verifiable from the repository: the Mac's working tree and ignored files,
Apple certificates and accounts, archives and App Store Connect state,
deployed DEV/PROD frontend SHAs, live backend environment values, Xcode build
success, physical-device behaviour, Dynamic Type coverage, and the status
indicator's actual position. These need a follow-up audit on the Mac, the
devices and the accounts.

## 11. Required iOS engineering handoff

At the end of every Mac or Windows iOS task, record in the PR or project notes:

- objective and screenshot or mockup reference;
- branch, local `HEAD`, remote SHA, and staged, unstaged, untracked and ignored
  native file status;
- changed files and the reasoning;
- DEV/PROD identities touched and the current native version and build of each;
- actual deployed DEV and PROD frontend SHAs, or `unverified`;
- tests run (unit, CSS contract, browser, Xcode, real device), each kept
  distinct;
- hardware, viewport, safe-area insets, active native layout classes and
  screenshots;
- incomplete work, known limitations, risks and the approved next action.

Never state that browser simulation proves real iOS geometry, that a pushed
commit is deployed, that a TestFlight upload is a public submission, or that a
local Mac change exists remotely, without verifying it.
